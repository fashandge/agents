# Architecture

Detailed module behavior for the `agents` library. `CLAUDE.md` has the short rules; this file has the full semantics and the why.

## Three layers (top-level `agents/` package)

1. **`env.build_env()`** — sources `~/.zshenv` on macOS or `~/.bashrc` on Linux plus `~/.config/secrets.env`, then returns an env dict suitable for `subprocess.run(env=...)`. Shell output is parsed as NUL-delimited records so multiline values cannot be truncated; exported `BASH_FUNC_*` functions are deliberately removed before agent, SSH, tmux, or `/bin/sh` subprocesses inherit the environment. This is the single entry point for getting a usable PATH and API keys inside launchd/cron contexts where the parent env is minimal. Other modules in this repo call it rather than reaching into `os.environ` directly.

2. **`coding_agents_cli`** — unified blocking interface for the three agent CLIs. The shape is:
   - `AgentType` enum (`codex`/`claude`/`gemini`) and `DEFAULT_MODELS` per agent.
   - `AgentConfig` dataclass: all options for all agents live here, prefixed by agent (`claude_*`, `codex_*`). `__post_init__` resolves defaults so callers never need a getter. Reasoning/effort is agent-specific: `codex_reasoning_effort` (string `low`/`medium`/`high`/`xhigh`/`max`, defaulted to `high` for `gpt-5.4-mini` / `medium` otherwise) is written to Codex's `model_reasoning_effort` config; `claude_effort` (string `low`/`medium`/`high`/`xhigh`/`max`, default `None`) is forwarded via Claude's `--effort` flag when set, and when `None` no flag is emitted so an ambient `CLAUDE_EFFORT` env var stays in effect. Both the `claude -p` and `claude-pty-wrapper` paths accept `--effort`. Gemini (`agy`) has no reasoning-effort surface.
   - Native review options remain agent-prefixed too. `codex_review=True` routes the supplied prompt through headless `codex exec review` as custom review instructions; `claude_review_command` prefixes the prompt with Claude Code's unnamespaced `/code-review` or `/review [target]`. Claude target combinations are validated in `AgentConfig.__post_init__`. The ordinary prompt path remains the default when no review option is set.
   - `run_with_config(prompt, config)` dispatches to per-agent internal runners; `run_with_config_and_fallback` walks `DEFAULT_AGENT_FALLBACK_ORDER` (Codex → Claude → Gemini).
   - Claude defaults to **direct `claude -p`** (`AgentConfig.claude_use_pty_wrapper` default `False`). Set it `True` to route through `claude-pty-wrapper` and drive the interactive Claude Code session while still returning print-style output.
     - **Why `-p` is the default (caveat):** the pty-wrapper drives the *interactive* Claude Code session, which starts plugin-provided MCP stdio servers (e.g. Playwright / chrome-devtools via `npm exec`). Those servers don't shut down on teardown and keep the wrapper's PTY slave open, so the master read never sees EOF — an otherwise-**finished** headless run hangs until its hard timeout (`subprocess.run(timeout=timeout+10)`) kills it, and the killed wrapper orphans the MCP servers (they accumulate as long-lived background processes). Direct `claude -p` neither hangs nor leaks (it reaps its own child MCP servers on exit), so it is the default for the unattended/launchd callers of this library (news summarizers, notes monitor, etc.). This is a bug in the wrapper's child-process teardown, not in Claude itself.
     - `AgentConfig.claude_disable_mcp` (default `False`) / `agents_cli --no-mcp` runs Claude with `--strict-mcp-config` + empty `--mcp-config` so no MCP servers start at all — extra hygiene for agents that need zero MCP tools (e.g. the notes monitor). On the `-p` path `--strict-mcp-config` fully suppresses plugin MCP; the wrapper forwards the flags too, but only `-p` reliably avoids spawning them.
   - Gemini calls are dispatched to the `agy` CLI, not the `gemini` CLI. The prompt is passed via stdin using `--print -` (not as an argv value) to avoid `ARG_MAX` limits on long prompts and to keep the invocation free of `shell=True`.

3. **Streaming variants** — same agent set, but yield `AgentStreamEvent`s as the process runs:
   - `coding_agents_streaming` is the top-level streaming dispatcher. It reuses `coding_agents_cli`'s command/env builders and Claude path is delegated to `claude_pty_wrapper_streaming`.
   - `claude_pty_wrapper_streaming` shells out to `claude-pty-wrapper -p --output-format stream-json` and converts the wrapper's JSONL into readable progress events plus a clean final assistant string. Do not switch this module to `claude -p` — the wrapper path is intentional.

## Shell entry point

`agents_cli.py` is a thin argparse-based shell entry point on top of `coding_agents_cli`. It accepts the prompt as an argv arg or via stdin, builds a single `AgentConfig`, and delegates to `run_with_config` — or, when `--fallback` is given, builds one `AgentConfig` per agent in the list and calls `run_with_config_and_fallback`. Only the first config in the fallback list receives `--model`; the rest fall back to their per-agent defaults. Effort flags: `--codex-reasoning {low,medium,high,xhigh,max}` maps to `AgentConfig.codex_reasoning_effort`, and `--claude-effort {low,medium,high,xhigh,max}` maps to `AgentConfig.claude_effort` (forwarded as `--effort`; when omitted the ambient `CLAUDE_EFFORT` env var stays in effect).

Native review flags are `--codex-review`, and `--claude-review-command {code-review,review}` plus optional `--claude-review-target` for `/review`. Codex receives the caller's prompt as native custom review instructions; an authoritative diff snapshot can therefore carry an exact staged, working-tree, branch, or commit-range candidate without combining the mutually exclusive native target flags and custom prompt. The parser rejects incompatible Claude target combinations before launching an agent.

`--detach OUTPUT_BASE` runs the call as a detached daemon via `coding_agents_cli.run_detached(runner, output_base)`: double fork + `os.setsid()` puts the agent in its own session (reparented to launchd), the CLI prints one JSON line (`pid` + result-file paths) and exits 0 immediately. The prompt is fully read from stdin *before* forking. Results are file-based — final answer in `OUTPUT_BASE.out`, log/stderr stream in `.err`, `.pid`, and `.exitcode` written last (pollers watch for it; an exception in the runner leaves a traceback in `.err` and exit code 1). The agent's own `--timeout` is enforced inside the detached process. Reason it exists: a cmux-hosted Claude Code session's idle reaper SIGKILLs background agent process groups ~6 minutes after the session goes idle (measured 2026-07-15; plain shells survive, detached runs survive) — so use `--detach` only for runs expected to exceed ~6 minutes in that environment; short runs keep the normal blocking contract.

## API clients (independent of the agent-CLI stack)

`openrouter` — `OpenRouterChatClient.complete(...)` posts to OpenRouter's chat completions endpoint, with a `RANDOM_FREE` model option that picks from `data/openrouter_free_models.txt` and retries across models on failure.

`deepseek` — a parallel, standalone client for DeepSeek's OpenAI-compatible chat completions endpoint: `DeepSeekChatClient.complete(...)` reads `DEEPSEEK_API_KEY`, defaults to model `deepseek-v4-flash`, and supports `max_tokens`, a `thinking` flag, and `reasoning_effort`. Known model ids live in `DeepSeekModel` (`deepseek-v4-pro`, `deepseek-v4-flash`, `deepseek-chat`, `deepseek-reasoner`). `thinking` defaults to `False`, which sends `{"thinking":{"type":"disabled"}}` to turn off the reasoning pass on hybrid V4 models (faster/cheaper); pass `thinking=True` to send `{"thinking":{"type":"enabled"}}`. When thinking is on, `reasoning_effort` sizes the reasoning depth — DeepSeek only honors `high` (default) and `max` (see `ReasoningEffort`; legacy `low`/`medium`/`xhigh` are server-mapped onto those), and it is ignored when thinking is off. Thinking mode also ignores `temperature` (no error, no effect). It shares no code with `openrouter` — both are deliberately small, self-contained, stdlib-only (`urllib`) clients.

## Messaging

`openclaw` is a thin wrapper around the `openclaw` CLI (`openclaw message send`) for delivering a message to any openclaw-supported channel (Discord, Slack, Telegram, iMessage, …). Unlike `openrouter`/`deepseek` it makes **no** direct network call — it builds an argv list and `subprocess.run`s the binary via `env.build_env()`, so auth/channel config lives in openclaw (no bot token in this repo) and it keeps working under launchd/cron. `send_message(message, *, channel, target, ...)` is the generic primitive; `send_discord(message, channel_id=DEFAULT_DISCORD_CHANNEL_ID, ...)` is a convenience that fixes `channel="discord"`, formats the `channel:<id>` target, and truncates to Discord's 2000-char limit (`DISCORD_MAX_CHARS`). Both raise `RuntimeError` on a non-zero openclaw exit. Also runnable as a CLI: `python -m agents.openclaw --message "..." [--channel slack --target channel:C01] [--dry-run]`. The notes-system monitor's `notify.py` is a thin shim over `send_discord`.

## Durable agent handoff

`orchestration/handoff.py` and `orchestration/handoffctl.py` implement the local-v1 protocol originally specified in `docs/2026-07-14_agent-handoff-communication-design.md`; this section is authoritative for the collapsed lifecycle introduced on 2026-07-22. The inbox/outbox JSONL files are authoritative and append+`fsync` occurs before atomic replacement of the owned `control.json`/`status.json` projection. Current worker states are `starting`, `working`, `blocked`, `awaiting_review`, and `paused`: an accepted review alone lets the worker checkpoint `paused`, and a work message newer than that review resumes it. Fatality is not a state; it is derived from a fatal outbox event in the live worker epoch. `succeeded`, `stopped`, `failed`, `pause`, `stop`, and `control.desired_state` remain permanently readable for historical journals and snapshots but cannot be written by a new run. Role locks cover the complete append/project operation; orchestrator and worker credentials are independent, epoch-fenced 32-byte tokens whose hashes alone appear in the run directory. `doctor` is read-only unless an explicit repair flag is supplied. Repair never silently removes corruption: a partial final record is quarantined, while mid-file and semantic corruption remain fatal. The `emit` data-payload schemas (checkpoint/question/result/error) have one source of truth, the `EMIT_DATA_SCHEMAS` constant in `handoff.py`: it feeds the exact-field validator errors, the `emit --help` epilog, and the generated kickoff contract, so a worker never needs to read source to construct a valid `--data-file` and a rejection enumerates the full expected shape in one round-trip.

`orchestration/handoff_registry.py` maintains a mode-`0600` orchestrator-side registry (default `~/.local/state/agents/handoff/registry.json`). Each owner-side launch records its exact run directory, transport handle, model, observer cursor, optional `orchestrator_id`, explicit `finished_at` marker, and private credential directory; a remote launch also records a credential-free proxy entry on the caller. `conclude --stop` writes the marker only after review and integration are durable; `stop` writes the same marker for an already-paused run, and both operations are idempotent. Remote responses mirror the owning host's marker into the caller-side proxy so the local watcher can quiet the run. Public `runs`/`context` output redacts the credential directory. Legacy records remain deliberately unowned until `runs adopt` associates one with an exact orchestrator session.

Teardown is one command, `runs clean` (implemented in `orchestration/handoff_clean.py`): `--run <selector>` cleans one run immediately; without it, bulk mode previews with `--dry-run` and requires `--yes`, with `--older-than` days against `registered_at`, `--host`, and `--watcher-state`/`--orchestrator` filters. `--dead`, `--fatal`, and `--finished` are composable fact filters. A run is reapable when the orchestrator marked it finished, its live worker epoch contains a fatal event, its run directory is missing, or the session transport answered that the session is absent. Transport failure is unknown liveness and always skips; it is never treated as absence. Remote facts and cleanup are evaluated on the owning host by an SSH probe before the local proxy record is removed. Cleaning kills the run's leftover worker session if one still exists (remote tmux via the probe, local tmux directly, a local cmux surface closed by exact UUID with before/after layout verification), then drops the registry record; `--force` cleans runs not otherwise reapable, but does not override unknown transport liveness. Neither session killing nor record removal ever touches a run directory, journal, or credential file unless `--delete-run-dir` is passed, which removes each cleaned run's directory (never the separate credential directory) — locally or, for a remote run, on the owning host — refusing directories without `status.json`; otherwise a cleaned run stays inspectable by absolute `--run-dir`. Historical terminal snapshots and `desired_state == "stop"` remain accepted only as read tolerance. `runs doctor` reports per-record validity without failing the whole read, so one corrupt entry degrades to a named record to clean instead of taking down every registry read; strict validation on the normal read paths is unchanged.

Host updates use `scripts/update_agents.sh` so `git pull --ff-only` and all cumulative idempotent state migrations run together. The journal-state migration maps historical `succeeded`/`stopped` snapshots to `paused`, removes `desired_state`, backfills local finished markers, and reconciles remote markers from the owning host; an unreachable remote host is reported and left for a later retry. Every write run first backs up the complete state tree. `--no-pull` migrates only; `--dry-run` skips the pull and previews every migration without writing state.

`orchestration/handoff_watcher.py` implements the detached, session-owned delivery adapter. Its mode-`0600` atomic snapshot lives in a mode-`0700` orchestrator directory, stores the exact tmux handle, cmux workspace/surface pair, or native-app thread ID, and contains no role or recovery credential. It also stores the owning orchestrator PID plus its process-start token; the watcher exits when that exact process disappears or the PID is reused, and suppresses polling and doorbells while liveness is temporarily unverifiable. A nonblocking lifetime lock enforces one watcher for the state file, while `orchestrator start` serializes check-and-start and reuses the existing singleton whatever its hosting mode. Every poll reloads the registry, selects only the matching `orchestrator_id`, validates local or remote outbox state, records `observed_through` before push, and coalesces all due runs into one canonical doorbell. The doorbell is the opaque snapshot pointer (orchestrator ID only, never event bodies): for a cmux orchestrator it attempts two complementary channels — typed input into the orchestrator surface, the only channel that pushes a hosted agent to read its pending outboxes, counted as delivered only when the text visibly echoes on the surface afterward (a zero exit from `cmux send` alone proves nothing, and code-mode/desktop-backed surfaces never echo), plus the surface's native visible `cmux notify` alert for the human, falling back to a workspace-level alert and, only when no channel accepted, a macOS notification; tmux orchestrators keep terminal-input doorbells since tmux has no native alert. The typed channel writes into the same composer the human types into, so it is gated by a composer guard before any keystroke is sent. An empty composer sends immediately, which also covers a running turn, since input typed mid-turn simply queues. A draft on a surface that does not currently have user focus — cmux is not the frontmost application per `lsappinfo`, or the surface is not the selected one in the focused pane's `list-pane-surfaces` listing — cannot be receiving keystrokes however busy the keyboard and mouse are elsewhere, so it is forced at once; this is deliberately a focus test rather than a machine-wide idle timer, which cannot tell typing here from typing in another app. A draft on the focused surface is sampled for `COMPOSER_STABLE_SECONDS`: any edit defers the typed channel to a later poll, and text that never changes is treated as parked and forced. A forced doorbell prefixes a fixed warning telling the orchestrator that the text before it is an unfinished human draft, to ignore it, and to quote it back verbatim, because submitting clears the composer and the draft is otherwise unrecoverable; the pointer sentence stays a contiguous suffix so echo verification looks for it alone. A guard that cannot read the surface resolves to send-immediately rather than withholding doorbells. `doorbell_through` records attempts; only `control.outbox_cursor` records semantic consumption. Each attempt is recorded as `last_doorbell_at` plus the accepting channel(s) in `last_doorbell_method` (a `+`-joined subset of `cmux_input`, `cmux_input_forced`, `deferred_input`, `cmux_notify`, and `cmux_notify_workspace` for cmux, or `macos_notification`, `terminal_input`, `native_app`); acceptance means the transport acknowledged the request — plus a visible echo for `cmux_input` — never that the user saw the alert, and a failure of every channel nulls the method and stores the combined `last_doorbell_error`. A `deferred_input` method means the typed channel was withheld because a live draft sat in the composer: the delivery cursors and `last_doorbell_at` are deliberately left untouched so the very next poll retries instead of waiting out the retry interval, while the visible alert has still fired. Watcher hosting is mode-selected (`orchestrator start --mode auto|detached|surface`). tmux and native-app orchestrators keep the fully detached daemon, deliberately orphaned (reparented to launchd) to escape the cmux idle reaper; but the cmux server rejects socket calls from clients outside its own process tree under the default `automation.socketControlMode: "cmuxOnly"`, so from a detached watcher every cmux command fails fast and the recorded method degrades to the `macos_notification` fallback. cmux orchestrators therefore default (`auto`) to a surface-hosted watcher: `orchestrator start` creates a dedicated cmux terminal surface — named `watcher: <orchestrator workspace title>` (a short orchestrator-ID suffix is appended only when that name is already taken — names are cosmetic, all addressing is by surface UUID) and parked with its peers in a `handoff-watchers` workspace kept at the bottom of the sidebar rather than in the working workspace — and runs `handoffctl watch --orchestrator-state …` in its foreground, keeping the watcher inside the cmux process tree so typed doorbell input and native `cmux notify` alerts both work without any `socketControlMode` relaxation. The hosting tab doubles as the watcher's log — orchestrator watch mode prints a credential-free JSONL poll summary (run IDs and cursors only) whenever a poll attempted a doorbell or hit an error — and its lifetime is surface-bound: closing the tab (or the `handoff-watchers` workspace) kills the watcher, the next `orchestrator start` relaunches it, and the owner-process exit check is unchanged. A hidden in-tree watcher is not possible: the socket ACL walks live process ancestry to the cmux app, the app durably parents only surface shells, and `pipe-pane` commands are spawned by the invoking CLI process rather than the app, so they die out-of-tree with their launcher. An explicit `--mode detached` for a cmux orchestrator remains allowed and accepts the degraded macOS-banner fallback; cmux's documented `socketControlMode: "password"` plus `socketPassword` (with `CMUX_SOCKET_PASSWORD` available via `~/.config/secrets.env`) remains the unverified escape hatch if native cmux alerts from a fully detached daemon are ever required. Failed or crash-interrupted delivery therefore remains pending and is retried with bounded backoff. Partial prefix consumption triggers a new doorbell for the remainder. The native-app routing hook preserves the exact registered thread ID and durable pending state when no provider-specific sender is installed.

For local coordination on the Mac, use the exact interpreter path in this repository:

```text
/opt/homebrew/Caskroom/miniconda/base/envs/ml/bin/python -m agents.orchestration.handoffctl --help
```

Registry-aware operations use a run ID, unique prefix, name, handle, or URI:

```text
handoffctl runs list
handoffctl orchestrator register --state /absolute/orchestrator/watcher.json --transport tmux --target session:pane --owner-pid PID
handoffctl orchestrator start --state /absolute/orchestrator/watcher.json --interval 5 [--mode auto|detached|surface]
handoffctl runs adopt --run <selector> --orchestrator-state /absolute/orchestrator/watcher.json
handoffctl runs clean --run <selector> [--force] [--delete-run-dir]
handoffctl runs clean [--older-than DAYS] [--host NAME] [--watcher-state PATH | --orchestrator ID] [--dead] [--fatal] [--finished] [--force] [--delete-run-dir] (--dry-run | --yes)
handoffctl runs doctor
handoffctl context --run <selector>
handoffctl dispatch --run <selector> --body-file -
handoffctl conclude --run <selector> [--stop]
handoffctl stop --run <selector>
handoffctl watch [--run <selector> ...] --interval 5 [--timeout 300] [--notify-cmux]
handoffctl orchestrator pending --state /absolute/orchestrator/watcher.json [--full-context]
```

`dispatch` is deliberately one-shot. On the owning host it validates that no live orchestrator lease exists, uses the registered recovery credential to acquire a fresh epoch, and appends the instruction. If the worker is already `awaiting_review`, it first consumes the current outbox prefix and sends a `supersede` message tied to the exact pending result; that auditable message permits the worker to checkpoint back to `working` without accepting or mislabeling the old result. It then rings the exact tmux/cmux handle with only the run ID and inbox sequence, releases the lease, and deletes the ephemeral orchestrator token. Remote dispatch sends the instruction on SSH stdin and performs the entire owner-side operation, including the tmux doorbell, in one SSH invocation.

`send` is the managed orchestrator's message verb (answer/review/steer and input/base changes) while it holds the lease. Work messages remain deliverable after a per-result integration decision so an integrated, paused worker can start another work cycle. After appending the durable inbox message it resolves the run in the local registry and, by default, rings the worker's tmux/cmux doorbell with the new inbox sequence — best-effort like the dispatch ring: the durable message remains authoritative, the response reports `doorbell_sent`/`doorbell_error`, and unregistered or remote-host records skip the ring with an explanatory note. `--no-doorbell` opts out for callers that know the worker is already awake.

`context` returns the immutable kickoff, run/control/status projections, progress log, and unread inbox/outbox records from the owning host. The original temporary kickoff source remains disposable after launch because `initialize` has already copied it into the durable run. Without `--orchestrator-state`, `watch` preserves the generic behavior: it polls one or more registered outboxes, prints each new event as JSONL, optionally emits metadata-only cmux notifications, and advances only its private registry observer cursor. Orchestrator mode is mutually exclusive with generic run selection, timeout, one-shot, and per-event cmux notification options. It reloads registry membership on every iteration and never changes the generic observer cursor or `control.outbox_cursor`, reviews a result, answers a question, or writes a worker inbox.

`orchestrator pending` is the normal user-turn recovery check. Its hot path returns only exact status/control snapshots and the unread outbox interval covered by the watcher snapshot. `--full-context` selects the existing durable `context` bundle for compaction, resume, takeover, ambiguous memory, or a mismatch between remembered and filesystem state. Normal handoff orchestration lazily registers and starts one watcher on the first worker launch, then passes `--orchestrator-state` to every later local or remote launcher so the watcher discovers each worker on its next poll. Unmonitored fire-and-forget is an explicit exception rather than the orchestration default.

`orchestration/handoff_launcher.py`, invoked by `scripts/handoff_agent.sh`, is the local cmux/tmux session adapter for Claude Code, Codex, and Kimi Code. Its defaults are Claude `opus/high`, Codex `gpt-5.6-terra/xhigh`, and Kimi `kimi-code/k3`/`max`; `--model` and `--effort` override them. Kimi's namespaced alias is passed explicitly with `--model`, and `max` is exported as `KIMI_MODEL_THINKING_EFFORT`. With no backend override the launcher uses cmux only when the orchestrator process has an inherited `CMUX_WORKSPACE_ID` and the cmux connection is reachable. It resolves the actual selected workspace through `cmux current-workspace` and supplies that reference with every surface-targeted command, rather than trusting the inherited environment value as the workspace identifier; otherwise it uses tmux. It initializes the external durable run and protected credential files, writes a mode-`0700` Python wrapper plus mode-`0600` JSON config outside the run, and types only `exec <quoted-wrapper> <quoted-config>` into the terminal. The wrapper uses the interpreter that launched the module (not a Mac-only shebang), builds agent argv as a list, uses `env.build_env()`, exports the handoff run/token-file environment, and calls `os.execvpe`. The worker contract records that same interpreter in its `handoffctl` commands, so it remains valid on Linux and inside a dedicated virtual environment. Claude and Codex receive the kickoff as a literal argv element. Kimi's documented prompt flag is non-interactive, so its TUI is launched first and receives a short instruction containing the resolved absolute path to the run's `kickoff.md`; it never has to interpret the `HANDOFF_RUN_DIR` variable name.

SSH workers use the same launcher with `--remote-host HOST --remote-cwd /absolute/checkout` and an optional `--remote-python`. The host must already have SSH key authentication, tmux, the selected agent, and a compatible installed copy of this package. The Mac reads the kickoff (and optional `.goal`) and sends their bytes plus typed launch options as JSON on SSH stdin to a fixed, shell-quoted module command. The receiver creates only a temporary mode-`0700` source directory, initializes the authoritative run and credentials on the worker host, starts the worker in remote tmux, removes the temporary source, and returns an `ssh://` run URI plus remote run/session fields. Remote Codex adds one bounded startup check: after a 30-second ready timeout, the Mac captures the exact returned tmux handle once and sends `C-m` only when the pane leader is Codex and the screen exactly matches its folder-trust dialog for the requested checkout; it reports `folder_trust_rescued` or `startup_unconfirmed` and never loops. `run.json` records `ssh_tmux`; no active journal is copied or synchronized back to the Mac. All later `handoffctl` operations execute on the worker host over SSH. Launch-only releases its remote orchestrator lease normally. A managed SSH run requires a known mode-`0700` remote directory supplied through `HANDOFF_REMOTE_CREDENTIAL_DIR`; the launcher never prints that path or any credential contents.

For a cmux-hosted orchestrator, `scripts/cmux_ssh_tmux_quiet.sh` provides the native remote-tmux viewer for explicitly named worker sessions. It first tries the no-window RPC attach path, but verifies that each requested local workspace actually materializes; an acknowledged RPC without a view falls through to `cmux ssh-tmux --no-focus`. The helper then moves only the named mirror workspaces below the orchestrator workspace and minimizes the temporary mirror window, preserving unrelated remote sessions.

Four further helper scripts scriptify deterministic procedures that the `handoff-agent` skill previously spelled out as prose (each documents its contract in its header comment). `scripts/handoff_orchestrator_ensure.sh` is the idempotent session-watcher bootstrap: it creates the private mode-`0700` orchestrator state directory when needed, runs `orchestrator register` (cmux resolves the surface from `CMUX_SURFACE_ID`; tmux requires `--target`) plus `orchestrator start`, and prints one JSON line with the state path and whether this invocation registered/started. `scripts/handoff_doorbell.sh` is the manual doorbell fallback with the bracketed-paste submit discipline built in (text and Enter as separate sends ~1s apart, pane capture, one retry Enter); its body is always the fixed opaque `Check handoff run <id>; inbox now through seq <N>.` template and it never accepts arbitrary message text. `scripts/cmux_close_surface_safe.sh` is the only sanctioned way to close a viewer tab: it snapshots pane-surfaces and workspaces, closes exactly one surface by UUID, re-lists, and fails loudly if anything else disappeared — never `close-window`, `close-workspace`, or a `tab-action` sweep. `scripts/tmux_run_logged.sh` runs a batch command in a detached tmux session with output tee'd to both the pane and a logfile, appending `EXIT:<code>` from `PIPESTATUS[0]` so viewers can distinguish progress from failure.

The launcher primitive returns quickly by default: after creating the session (and delivering Kimi's run-specific kickoff pointer), it releases the orchestrator lease and returns without polling semantic readiness. Codex is the narrow exception: remote Codex asks the remote launcher for the first ready checkpoint for 30 seconds, then conditionally makes one exact screen capture and one `C-m` folder-trust rescue as described above, and local Codex gets the equivalent rescue in the launched cmux/tmux surface — it polls the surface for up to 30 seconds and presses Enter once on Codex's exact folder-trust dialog for the launch `cwd`, reporting `folder_trust_rescued` (or `startup_unconfirmed` for a dialog naming any other directory). Because a narrow surface truncates or wraps the `You are in <cwd>` line, the local check verifies the directory by prefix rather than exact string, and an already-trusted directory returns after a short grace instead of blocking the full timeout. Normal orchestration still supplies the session's `--orchestrator-state`, so this fast return does not disable detached outbox monitoring; omitting orchestrator state is the explicit fire-and-forget path. cmux probes request `--id-format both` so the UUID returned by `new-surface` remains comparable with later surface/process inventory. Kimi uses the normal readiness timeout (120 seconds by default) as one shared startup budget for both process discovery and the later appearance of its empty input widget. Native process visibility can precede input readiness, either phase can legitimately take more than 10 seconds, and terminal input sent during that gap can be echoed into scrollback and dropped. Both adapters first submit that Kimi instruction with `Ctrl-J`, because a synthetic `Enter` can become an input newline on some versions. They then require a newly visible instruction after the TUI banner, inspect the input row, and fall back once to `Enter` when the instruction remains pending, which is required by Kimi 0.27.0 through cmux; if neither key produces that evidence, `kickoff_sent` is false and the launcher reports a rescue command. Shell launch commands and ordinary doorbells retain normal `Enter` behavior. `--wait-ready` opts into the process-plus-checkpoint wait, and `--retain-orchestrator` keeps the lease for an active monitoring loop. A caller-supplied `HANDOFF_CREDENTIAL_DIR` is used as the exact private directory with fixed token filenames, eliminating filesystem discovery. If a sibling `.goal` file exists for Claude or Codex, its first line is still sent only after both the session/process probe and a worker-written status revision prove readiness; timeout leaves the run and session intact and reports a capture/rescue command. Workers publish the canonical first checkpoint with the idempotent `handoffctl ready` command. Result publication verifies that the worker reports the current Git `HEAD` and dirty state truthfully; pre-existing or intentional uncommitted changes do not make publication impossible and remain subject to orchestrator diff review. Once a result is durably published and projected to `awaiting_review`, `handoffctl` attempts `cmux notify --surface "$CMUX_SURFACE_ID" --title "Handoff result ready" --body "Awaiting orchestrator review"` for a cmux-transport run. The alert is best-effort: absence, timeout, or failure of cmux never rolls back or invalidates the durable result.

The launcher prints the selected agent/model/effort, run directory, transport handle, readiness/kickoff state, and whether orchestrator ownership was released, but not credential contents or paths. Managed orchestrator automation should retain its fixed protected credential path, renew the 180-second lease during idle periods, and use journal message IDs for retry idempotence.

Session closure has separate transport and protocol semantics. An explicit operator request to close/kill a named worker is handled immediately against its exact launch handle (`cmux close-surface --surface HANDLE` or `tmux kill-session -t HANDLE`), without first acquiring orchestrator ownership or waiting for a worker acknowledgment. Review and finished-marker writes remain protocol workflows when the caller explicitly requests progress preservation or semantic completion; no worker `stop` message or exit checkpoint exists for current runs. Closing a transport can therefore leave the durable run unmarked; the positive-absence transport fact makes it eligible for later cleanup without inventing protocol state.
